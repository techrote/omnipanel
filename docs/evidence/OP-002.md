## Schema inventory and invariants

`docs/SCHEMA_CONTRACTS.md` is the full inventory. The load-bearing implementation
properties are summarized here.

### Closed versioned records

Top-level records carry exact integer `schema_version = 1`. Unknown/future versions,
string/bool/float coercions of that version, unknown fields and unknown enum values fail
validation. Models are immutable and collections participating in identity relationships
are bounded; duplicates are rejected where semantically ambiguous.

This is a migration hook rather than migration implementation: a future generation must
be selected/migrated explicitly before constructing a current typed record. OP-003 still
owns durable state and migrations.

### Identity

Authoritative stable IDs are distinct fields from display text. Renaming a display name
cannot change a task/metaissue/project/run/model/component identity. Model identity uses
provider + model IDs; component contracts use component + contract + version. The schema
does not infer identity from Markdown, aliases or UI labels.

### Policy and review floors

The selected programme dimensions are represented directly: Tissue/Labware/Stone/Steel,
expected value, expected wall time, marginal cost, Single/Race/Diversity and the five
named Race policies.

Stone requires an independent implementation review. Steel requires an independent
implementation review, an independent verification review and explicit user adjudication
before consequential promotion. Steel/priceless/days/paid policies can exist without a
human choice but remain explicitly undecided until a structured user-decision record is
present; the schema does not silently invent authorization.

### Authority defaults and evaluator separation

Provider requests default to no capability handles, no writable paths, no network, zero
requested resources and isolation required. Resource quantities use explicit integer
units. There are no token/password/secret fields.

Hidden acceptance gates must be master-only and require an independent evaluator context.
Gate outcomes distinguish PASS, FAIL and NOT RUN. Candidate success therefore cannot be
serialized as merge/deploy authority by accident.

### Runs, safety and cancellation

Single runs require exactly one candidate; Race requires at least two plus an explicit
named Race policy; Diversity requires at least two and rejects Race policy. Selected
candidates must belong to the run.

Only model safety state `active` is automatically schedulable. `quarantined` and
`verboten` are fail-closed snapshots; automatic transition/reversal enforcement remains
later work.

Normal cancellation without retained salvage must explain why salvage was unavailable;
retained salvage requires evidence references. Emergency containment may have no salvage,
preserving the programme rule that containment outranks cooperative cleanup.

## Dependency rationale

Pydantic `2.13.5` is the direct OP-002 validation dependency. It provides the strict
closed-model validation, immutable records, typed nested contracts and JSON
serialization/schema support needed at this boundary without introducing persistence,
networking, scheduling or provider authority. Textual `8.2.8` remains the OP-001
presentation dependency and is not imported by domain contracts.

The project continues to use direct pins rather than claiming a complete transitive
lockfile. The CI artifacts retain the actual resolved environment for each matrix job.
